space.grooveshop.payments

UCP payment handler specification · version 2026-08-25 · protocol UCP 2026-08-25

Scope

This handler covers payment methods a business settles outside the agent conversation, where the platform submits no payment credential. Selecting the instrument is the whole payment authorisation the business needs in order to place the order; funds move later, between the buyer and the carrier.

Because no credential is transmitted, no participant enters PCI DSS scope for any instrument in this handler. The instrument schema enforces that structurally: credential is false, so a declaration carrying one fails validation rather than relying on policy.

Card, wallet and other credential-bearing payments are out of scope. A business that only accepts those advertises no handler, and its checkouts escalate to the web with requires_escalation and a continue_url.

Participants

ParticipantRole
BusinessAdvertises the handler, resolves the instruments available for a given checkout, and places the order on completion. Appears as merchant in some UCP field names.
PlatformDiscovers the handler, presents the instruments to the buyer, and submits the selected instrument on checkout completion.
CarrierCollects funds from the buyer on delivery and remits them to the business. Never a UCP participant: it exchanges no protocol messages.

Prerequisites

Business
Configures at least one active offline payment method carrying a provider code. No processor onboarding, identity, or key material is required: nothing is charged through this handler, so there is no credential to authenticate and no secret to publish. The handler therefore declares no PaymentIdentity.
Platform
None. Any platform that can read the business profile can use this handler.

Handler declaration

The business advertises the handler at /.well-known/ucp, one entry per store, listing one instrument per active offline payment method in its own preferred presentation order.

{
  "payment_handlers": {
    "space.grooveshop.payments": [
      {
        "id": "grooveshop_payments",
        "version": "2026-08-25",
        "spec": "https://payments.grooveshop.space/2026-08-25/",
        "schema": "https://payments.grooveshop.space/2026-08-25/schema.json",
        "available_instruments": [
          {
            "type": "cash_on_delivery",
            "constraints": {
              "properties": { "provider_code": { "const": "cash_on_delivery" } }
            }
          }
        ],
        "config": { "environment": "production" }
      }
    ]
  }
}

Config

FieldRequiredDescription
environmentyes sandbox or production. Only the production deployment reports production; platforms use it to keep test traffic out of live order flow.
settlementresponse only Fixed at on_delivery. States when funds are expected to move.

Constraint target

available_instruments[].constraints describes the instrument schema's $defs/constraint_target, which declares one member: provider_code, the business's own identifier for the settlement provider. It is derived from business configuration and never carried in a payload, which is why it is expressed as a constraint rather than as a request requirement.

Supported instruments

TypeCredentialDescription
cash_on_deliverynone The buyer pays the carrier when the order arrives. The business may add a surcharge, already reflected in the checkout totals and echoed on the instrument's display.fee.

The instrument type vocabulary is open and additive: a new settlement method ships as a new instrument type under a new handler version, never as new bytes at this version's URLs.

Instrument acquisition

There is nothing to acquire. No tokenisation endpoint exists, no credential is collected, and no binding is required — binding guards credential replay, and this handler transmits no credential. The platform constructs the instrument directly from the resolved declaration:

{
  "payment": {
    "instruments": [
      {
        "id": "instr_1",
        "handler_id": "grooveshop_payments",
        "type": "cash_on_delivery",
        "selected": true
      }
    ]
  }
}

handler_id MUST equal the id of the handler declaration the instrument came from. type MUST be one the authoritative response advertised for that checkout; the response is authoritative even where it narrows what the profile advertised.

Processing

  1. The business re-resolves the instrument against the checkout: the type must still be available, and the pay-way behind it must still be active.
  2. The business places the order, recording the settlement method so fulfilment instructs the carrier to collect on delivery.
  3. The checkout reaches completed and carries the order confirmation. No authorisation, capture, or settlement call occurs at completion — funds move on delivery.

Errors

ConditionBehaviour
Instrument type not available for this checkout Recoverable error naming the offending path; the platform may resubmit with an advertised type.
Business has no active offline method No handler is advertised at all, and the checkout escalates with requires_escalation plus a continue_url.

Security

  • No credential handling. The instrument schema forbids credential, so no participant can transmit card data through this handler even by mistake, and none enters PCI DSS scope.
  • No tokens, therefore no expiry and no replay window. Binding is not required because there is no credential whose reuse could be replayed.
  • Authority binding. These documents are served from payments.grooveshop.space, whose reversed labels equal space.grooveshop.payments — the exact-match case. A platform MUST reject the entity if the schema origin is not name-aligned.
  • Selecting the instrument is the authorisation. A business exposing this handler accepts an unfunded-order risk (refused delivery) in exchange for agent-completable checkout, and should apply the same order limits and fraud controls it applies to cash on delivery placed on the web.
